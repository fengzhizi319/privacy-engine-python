# Python 引擎算法与性能优化

> **组件归属**：`services/privacy-engine-python`
> **Go 对照**：上游 `services/privacy-engine/docs/算法优化.md`
> **定位**：记录 Python 实现中**已落地**的优化、**已识别但未解决**的瓶颈，以及可执行的优化路线。本文不复制 Go 侧结论；所有条目均以 Python 代码位置为依据。

---

## 1. 性能模型：先理解 Python 的边界

Python 引擎与 Go 的性能模型不同，优化前必须区分以下事实：

| 维度 | 现状 | 含义 |
|---|---|---|
| 进程模型 | `engine.server` 单进程；可选 `engine.launcher` 多进程（`PRIVACY_WORKERS`，默认 `min(cpu, 8)`，`SO_REUSEPORT`） | 多核扩展主要靠**多进程**，不是多线程 |
| REST 执行 | 路由绝大多数是同步 `def`，由 Starlette/AnyIO 线程池执行；仅文件上传与 Arrow IPC 等少数为 `async def` | CPU 密集请求受 **GIL** 与线程池上限约束 |
| gRPC 执行 | `grpc.max_workers`（`PRIVACY_GRPC_MAX_WORKERS`，默认 64/进程） | 每个 RPC 占一个工作线程，长计算会耗尽线程池 |
| 内存状态 | 每进程独立：分类 LRU、规则引擎 LRU、医疗缓存、预算内存态、限流器 | 多 worker 下缓存命中率按进程切分；限流/预算跨进程需 Redis/SQLite |
| 指标 | Prometheus 每进程注册表，无 multiprocess 聚合 | `/metrics` 只反映被抓取的那个 worker |
| 数值库 | NumPy / SciPy 在 C 层释放 GIL；pandas / PyArrow 同理 | 向量化路径可真正并行；纯 Python 循环不能 |

因此：**先用向量化减少 Python 级循环，再用多进程扩展多核，最后才考虑异步/批处理**。单纯增加线程通常不会提升 CPU 密集吞吐。

## 3. 已识别瓶颈与优化建议

按优先级排序：P0 影响正确性/安全，P1 影响高并发吞吐，P2 属常规优化。

### 3.1 P0：分类缓存保留原始 PII

**位置**：`engine/dynclassification/service.py:316-317, 365, 384`

```python
val_key = val_str_raw if len(val_str_raw) <= 200 else (len(val_str_raw), val_str_raw[:100], hash(val_str_raw))
cache_key = (domain or "", standard or "", field_name, val_key, sanitize)
...
field_result = FieldClassificationResult(field_value=str(value), ...)
...
self._classification_cache.put(cache_key, response)
```

问题：

1. 值 ≤200 字符时，**原值直接作为缓存键**；>200 字符时仍保留前 100 字符。
2. 缓存的 `ClassificationResponse` 内含 `field_value`（原始 PII）与可能的 `sanitized_value`，最多 10000 条常驻进程内存。
3. `hash()` 为进程级随机盐，跨重启不稳定，不能作为跨实例缓存键；且截断前缀仍可能包含敏感信息。

建议：

- 键统一改为 `sha256(value)` 截断（与规则引擎一致），不保留任何明文前缀；
- 缓存值剔除 `field_value`，只缓存标签/等级/置信度/审计元数据；`sanitize` 产物按需重算或不缓存；
- 为缓存增加命中率与条目数指标，支持容量与 TTL 配置。

验收：`grep` 不到原始值进入键；缓存条目序列化后不含 `field_value`；压测下命中率与改造前持平。

### 3.2 P1：个性化 profile 每请求读盘 + 全局锁

**位置**：`engine/privacy/profile.py:231-247`

```python
personalized_path = os.environ.get("PRIVACY_PERSONALIZED_PROFILE", "config/personalized-profiles.yaml")
if os.path.exists(personalized_path):
    with _profile_lock:
        with open(personalized_path, encoding="utf-8") as f:
            personalized_data = yaml.safe_load(f) or {}
```

问题：只要请求带 `namespace`（DP/K- Ano/QOL 默认路径），每次参数解析都会：

1. `os.path.exists` + `open` + 完整 YAML 解析；
2. 在**进程级全局锁** `_profile_lock` 内完成，所有请求串行化。

在推荐参数高频读取的场景，这是明显的吞吐瓶颈与尾延迟来源。

建议：

- 与 `ParameterResolver` 的基 profile 一致，按文件 `mtime + size` 缓存解析结果；
- 读盘在锁外完成，锁内只做原子指针替换（两阶段提交）；
- 或由 `PUT /v1/privacy/profile/...` 写入时主动更新内存快照，读路径零 I/O；
- 增加 `profile_reload_total` / `profile_load_duration_seconds` 指标。

### 3.3 P1：预算每次消耗新建 SQLite 连接 + 同步审计追加

**位置**：`engine/privacy/budget.py:255-283, 479-540, 71-99`

现状与权衡：

- `_db_conn` 每次操作 `sqlite3.connect` 并在结束时关闭。这是为修复 thread-local 连接泄漏而做的**有意设计**，不是疏漏；但每次 `spend` 都有连接建立、`PRAGMA` 设置、WAL 检查的固定成本。
- `BudgetAuditLogger.log_spend` 在锁内 `open(..., "a")` 追加一行并关闭，未 `fsync`；高 QPS 下形成文件系统元数据压力。
- 内存路径与 Redis 路径无此开销，但 SQLite 是单机持久化的默认选择。

建议（保持无泄漏前提）：

1. 引入**短生命周期连接池**（如每线程一个连接 + 定期回收 + 显式 `close` 钩子），避免每次 connect；或
2. 批量预算核销：同一请求内多个原语合并为一次 `spend`（接口层聚合），减少事务次数；
3. 审计日志改为有界队列 + 后台批量 flush，保留 HMAC 链；进程退出时强制 flush；
4. 压测确认 `BEGIN IMMEDIATE` 争用与 WAL 增长，必要时分命名空间分库。

> 不要简单恢复长期存活的 thread-local 连接；线程池线程退出时不会触发关闭，会重新引入 fd/WAL 泄漏。

### 3.4 P1：批量脱敏仍逐元素调用 `mask_value`

**位置**：`engine/privacy/masking.py:583-650, 1054`

- `mask_value_batch` 对每个元素调用一次 `mask_value`，每次都执行参数校验、`guess_field_type`（有 LRU）、Prometheus Counter/Histogram 采样与日志调用；整批只记一次指标，但内部仍逐元素埋点。
- `mask_dataframe` 的 pandas 路径对每个单元格 `.apply(lambda ...)`，并对所有非空值做 `str(val)`，数值列也会被转成字符串再判断类型。

建议：

- 批量接口先按 `field_name` 预计算 `FieldType`，再走类型专用循环；避免重复校验与指标开销；
- pandas 路径按 dtype 选择列：仅对字符串/object 列执行脱敏，数值列跳过；对同构列使用 `Series.str` 向量化或 Arrow 路径；
- 将 Prometheus 采样从单元级函数下沉到批处理外层（需要拆分内部 `_mask_value_core`）。

### 3.5 P2：`classify_table` / `classify_record` 串行

**位置**：`engine/dynclassification/service.py:499-503, 417-422`

- `classify_table` 逐行调用 `classify_record`，`classify_record` 逐字段调用 `classify_field`；无向量化、无并发。
- 大表分类的耗时近似 `行数 × 字段数 × 单字段成本`，仅靠缓存降低重复值成本。

建议：

- 先做**列级批处理**：同一字段的整列值可共享字段名与规则集，按列执行规则匹配；
- 对无状态字段分类使用 `ThreadPoolExecutor` 受控并发（NumPy/正则可在 C 层释放 GIL），但必须限制并发度，避免与 gRPC 线程池/AnyIO 线程池叠加造成线程爆炸；
- 提供 `classify_table` 的分块流式接口，避免整表常驻内存。

### 3.6 P2：`HighConcurrencyLRUCache` 单锁

**位置**：`engine/privacy/high_concurrency.py:381-438`

所有 `get/put/clear` 共享一把 `threading.Lock`。分类缓存是高频路径，热点 key 下锁竞争会抵消缓存收益。名称中的「HighConcurrency」目前只体现在线程安全，不是分片无锁。

建议：按 key 哈希分片（如 16/32 片，各自 LRU + 锁），或改用成熟的有界并发缓存；同时导出命中率、条目数指标。

### 3.7 P2：高并发工具与 JIT 内核未接线

以下代码已实现但**无外部调用**：

| 模块 | 能力 | 现状 |
|---|---|---|
| `NoisePool`（`high_concurrency.py:44`） | 预生成噪声池，降低采样开销 | 未接线 |
| `BatchedBudgetSpend`（`:234`） | 合并预算核销 | 未接线 |
| `AsyncDynamicBatcher`（`:441`） | 异步动态批处理 | 未接线 |
| `ConcurrencyThrottle`（`:518`） | 并发闸门 | 未接线 |
| `dp_jit.py` 全部函数 | NumPy 向量化核（可选 Numba） | 未被 `dp.py` 导入；`HAS_NUMBA` 仅检测 |

建议：先以基准证明收益，再接线；不要为「看起来高并发」而引入额外队列与延迟。`dp_jit` 若接线，需对比 NumPy 路径的吞吐与首次编译开销。

### 3.8 P2：网关 P2C 无延迟感知

**位置**：`engine/gateway/balancer.py:781-791`

P2C 仅比较 `active_connections / weight`：

- 无法区分「连接少但后端已过载」与「连接少且空闲」；
- 慢节点会持续接收新请求，直到连接数上升。

建议：为节点维护滑动窗口 EWMA 延迟（成功请求才更新），P2C 评分改为 `load × (1 + ewma/基线)`；熔断与被动冷却已经存在，可复用其健康信号。

### 3.9 P3：其他

| 项 | 位置 | 说明 |
|---|---|---|
| `_funnel_cache` 无容量上限 | `dynclassification/service.py:164` | 键为 `domain:standard`，通常有界；若允许任意标准名，需加上限或白名单 |
| 规则引擎缓存不缓存带 `context` 的求值 | `engine.py:229-263` | 正常语义；若上层频繁传 context，会退化为无缓存 |

## 5. 优化路线（建议顺序）

1. **P0 缓存脱敏**：分类缓存键改为摘要、值剔除原始 PII；补测试断言。
2. **P1 读路径去 I/O**：个性化 profile 改为 mtime 缓存/写入时更新，去掉全局锁内的解析。
3. **P1 批量化**：`mask_value_batch` 预计算类型；pandas 按 dtype 跳过非字符串列。
4. **P1 预算写路径**：连接池或请求级合并核销；审计异步批量 flush（保证退出前落盘）。
5. **P2 缓存分片**：`HighConcurrencyLRUCache` 分片并导出指标。
6. **P2 表级分类**：列级批处理 + 受控并发 + 分块流式接口。
7. **P2 网关延迟感知**：P2C + EWMA。
8. **验证未接线内核**：用基准决定 `NoisePool` / `BatchedBudgetSpend` / `dp_jit` 是否接线，无收益则删除，避免维护幻觉。

每一步都应附带：改造前后基准数据、内存曲线、回归用例，以及「未使 PII 驻留时间变长」的确认。
